# Onboard a Board Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the skill `project-conductor` with an "Onboard a board" procedure that prepares a GitHub Project board and its repository for the conductor loop, and prove it on the scratch ground and in dry-run form on `raidenyn/line-mcp`.

**Architecture:** Skill text only: `SKILL.md` holds the procedure, its rules and the report format; `references/onboarding-github.md` holds every `gh` command with its read-check-write order, in the style of `skills/task-publishing/references/github-project.md`. No script. Proof is live runs of the procedure by an agent following the skill.

**Tech Stack:** Markdown Agent Skill, `gh` 2.105+ (REST and GraphQL), the repo's validators (`scripts/skills.py`, `claude plugin validate`, unittest, `npm test`).

**Spec:** `openspec/changes/onboard-board-procedure/specs/board-onboarding/spec.md`, with `design.md` and `brainstorm.md` in the same folder, and the RFC `openspec/design/archive/2026-11-unattended-task-runs/rfc-run-board-tasks-unattended.md` (Onboarding, Settings, Run record).

## Global Constraints

- Skill name `project-conductor`; folder, frontmatter `name` and marketplace `name` identical; marketplace `source` `./skills/project-conductor`; no `version` in `.claude-plugin/marketplace.json`.
- `description` starts with "Use when", at most 1024 characters, no `<` or `>`; frontmatter only spec keys.
- `SKILL.md` under about 500 lines.
- Frozen names, verbatim: repository variable `PROJECT_URL`; `.agents/harness.json` key `"project-conductor"` with `maxParallel` 2, `reviewRounds` 5, `reconcileMinutes` 30, `maxAttempts` 2; `.agents/hooked-rules/repo-run-models.md` with roles plan, review, implement; replaces `repo-review-models.md`.
- Board fields, verbatim: "Run phase" (single select: plan, implement, closeout, care), "Attempt" (number), "Run thread" (text). A field is never renamed.
- Task key form `<!-- task: <rfc-slug>/<milestone-slug>/<number> -->`, first line of the body.
- Settings branch `chore/project-conductor-onboarding`. Model defaults: plan Opus-5.5, review GPT-6.2-Sol, implement DeepSeek (exact id confirmed per run).
- `task-publishing` is not changed. No new dependency. English. Conventional Commits.

## Review Focus

- **Issue body with CRLF line endings or no trailing newline** — the key is prepended and every other byte survives; the reference says to write the body from the raw API string, and task 3's proof compares the remainder byte for byte.
- **Board items that are pull requests, draft issues or plan issues** — never keyed, never reported as keyless; the item query keeps only open `Issue` content of the repository and treats a `<!-- plan: ` first line as identified; checked in task 3 with a draft item and plan issue P, and on `line-mcp`'s plan issues #127–130.
- **Issue from another repository on the board** — not keyed and reported, because keys and numbers belong to the one repository; stated in SKILL.md and listed in task 3's report check.
- **More than 100 board items or repository issues** — every page is read (`--limit 1000` / `--paginate`), as `task-publishing` warns `item-list` returns 30 by default; the reference uses paginated forms only.
- **`.agents/harness.json` with 2-space vs 4-space indentation or key order** — other keys keep value and order; the proposed file is written with the existing indentation (default 2 spaces when new); checked in task 3 with a pre-seeded file holding another key.

### Task 2: Write the procedure and its reference

**Files:**
- Modify: `skills/project-conductor/SKILL.md`
- Create: `skills/project-conductor/references/onboarding-github.md`

**Interfaces:**
- Consumes: task 1's folder.
- Produces: the procedure that task 3 runs; the report format with five lists `Created / Changed / Reused / Pending / Could not do (owner step)`, and the line "Nothing changed." exactly when the run made no successful write. Pending, owner steps and unkeyed issues are listed on every run.

- [ ] **Step 1: SKILL.md.** Sections: what the skill is (the conductor; this version holds only "Onboard a board"); Inputs (board URL, repository `owner/name`, the three models, dry run yes/no, proceed without asking yes/no); Rules (survey first and show the plan; dry run writes nothing; look before every write; change only the variable, the three fields, the two files, the key line of issue bodies; delete nothing except the replaced `repo-review-models.md`, and that only when no other file refers to it or the person agreed to edit the references; trusted input as in the spec; run one onboarding per repository at a time; a failure on one step is reported and the others continue, except the keying step stops whole on a duplicate key or a truncated read); the seven steps in this order: preflight, `PROJECT_URL`, fields, settings PR, keys, approval rule, webhook pending; the report format. Each step names its reference section and the spec's requirement it meets.
- [ ] **Step 2: Reference preflight and variable.** Preflight: `gh auth status` (scope `project`), agent login via `gh api user --jq .login`, repository `permissions.admin/push`, owner, default branch, board readable by explicit number and owner. Variable: read with `gh variable list --repo <repo> --json name,value` (readable by a writer, as checked on `line-mcp`; an error → "unknown, owner checks"), write with `gh variable set PROJECT_URL --repo <repo> --body "<board URL>"` only when `permissions.admin` is true; otherwise print that exact command with the real board URL. A different existing value is a change, shown in the plan.
- [ ] **Step 3: Reference fields.** Match names exactly, case included; a case-only collision is an owner step. Read fields through GraphQL `node(id: <project id>) { ... on ProjectV2 { fields(first: 100) { nodes { ... on ProjectV2FieldCommon { id name dataType } ... on ProjectV2SingleSelectField { options { id name color description } } } } } }`, because `gh project field-list` shows no `dataType` for number and text fields. Create with `gh project field-create <n> --owner <owner> --name <name> --data-type SINGLE_SELECT|NUMBER|TEXT` (`--single-select-options "plan,implement,closeout,care"`); add missing options with `updateProjectV2Field` sending every existing option with its id, color and description (copy the warning from `task-publishing`); wrong `dataType` → report.
- [ ] **Step 4: Reference settings PR.** Read both files from the default branch and from `chore/project-conductor-onboarding` via `gh api repos/<repo>/contents/<path>?ref=<ref>`; merge the key with `jq` keeping other keys, their order and the file's indentation (2 spaces when new); before writing to an existing branch or reusing a PR, list every open PR from it without a base filter (`gh pr list --repo <repo> --head chore/project-conductor-onboarding --state open --json number,baseRefName,isCrossRepository,headRepository`); one with another base or `isCrossRepository` true is a conflict. Then take the PR's head SHA (`headRefOid`, or the branch ref when no PR is open) and use that SHA for every read: `gh api repos/<repo>/compare/<default>...<sha> --jq '.files[] | "\(.status) \(.filename) \(.previous_filename // "")"'`, normalizing a `renamed` entry (GitHub may report the roster swap as one) to `removed previous_filename` plus `added filename`; derive the expected set of (status, path) from the approved plan (harness.json `modified`/`added`; repo-run-models.md `added`, repo-review-models.md `removed` and agreed reference edits unless deferred) and read every path's content or absence at that SHA (contents API at `ref=<sha>`). Equal set and contents: reuse as is. The returned set a strict subset of the expected one, with each present file equal to its planned content: an earlier run's partial work, so build one commit on that SHA adding the rest and push it without force (`git push origin <commit>:refs/heads/chore/project-conductor-onboarding`, rejected if the remote head moved; then report the conflict). Before reusing as is, check the PR head is still that SHA. Anything else is a conflict: report it and do not push; write via a local clone in the scratchpad, one commit `chore: onboard project-conductor settings`, `gh pr create`; content equal on the default branch → reused, no branch. Roster: find references with a local `git grep -n 'repo-review-models'` in that clone; any hit outside the file defers the roster migration (no `repo-run-models.md`, old file kept) and reports the hits, unless the person agreed in the plan to edit them in the same PR. Source of the reviewer rows and presets: the old file while it exists, else the existing `repo-run-models.md`, so a run after the merge proposes nothing. Include the `repo-run-models.md` template: frontmatter `pointer:` line and the OpenSpec `skills:`/`commands:` triggers copied from veles's `repo-review-models.md`; a `Role | Model | Effort` table for plan, review, implement; a "Reviewer presets" section copied unchanged when replacing.
- [ ] **Step 5: Reference keys.** Board items through GraphQL `items(first: 100, after: <cursor>)` paged until `hasNextPage` is false (stop the step if a page fails), keeping `content { ... on Issue { number state repository { nameWithOwner } body } }`: open issues of `<repo>` only; pull requests and draft items are ignored. The whole first line is matched against `^<!-- task: [a-z0-9-]+/[a-z0-9-]+/[0-9]+ -->$` and `^<!-- plan: [a-z0-9-]+/[a-z0-9-]+ -->$` (CR tolerated at the end); a match counts as identified; a first line starting `<!-- task:` or `<!-- plan:` that does not match is reported as malformed and left alone. The milestone marker's RFC slug must equal the board readme's, else no key and reported. Readme marker via `gh project view <n> --owner <owner> --format json --jq .readme`; milestone marker via the milestones API; all keys via the paginated issues query of `task-publishing` (`^<!-- task: `), open and closed. Trust via GraphQL `issue { author { login } userContentEdits(first: 100) { totalCount pageInfo { hasNextPage } nodes { id updatedAt editor { login } deletedAt } } }`: trusted only if `hasNextPage` is false, no `deletedAt`, no null editor or author, no GraphQL error, and every login is the agent or the owner. Allocation in ascending issue number from one max per prefix. Just before each write, read again the body, the edit ids and `updatedAt`, the state, the board membership and the milestone, and the repository-wide key inventory (paged); skip on any change, and skip and report a proposed key that another issue now holds (never renumber silently). Save bodies with `gh api "repos/<repo>/issues/<n>" | jq -j '.body // ""' > <file>` under `set -o pipefail` (no added newline; `gh api --jq` takes no `-j`); use the same capture after the write; write with `gh issue edit <n> --repo <repo> --body-file` (never a bare number: it resolves against the current checkout) of the key line, `\n`, then the saved body; read back and compare byte for byte.
- [ ] **Step 6: Reference approval rule and webhook.** Rulesets: `gh api repos/<repo>/rules/branches/<default>` → a `pull_request` rule with `required_approving_review_count >= 1` means "yes" (proved on `line-mcp`, where classic protection answers 404). Classic: `gh api repos/<repo>/branches/<default>/protection` → `required_pull_request_reviews.required_approving_review_count >= 1` means "yes"; a 404 "Branch not protected" read with admin rights means none. "no" only when both were read and neither requires one; anything else "unknown". Owner step names the repository's Settings → Rules page URL. Webhook line verbatim: "Webhook: pending. Created by the task \"Repair claims, settle merged work and wake on events\"."
